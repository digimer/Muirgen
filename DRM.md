# Muirgen Cryptographic and DRM Architecture

In order to provide red-monochrome maps that are legible, we must have access to raw S-75 vector files. In Canada, these can be purchased clear, but several other sources will require license agreements. 

To been the license requirement, and to ammortise the high investment costs of a central DB of many geographic areas, we'll need to eventually introduce a subscription service (similar the navionics). This will require introducing DRM, and this document describes the planned approach. 

Note that the primary focus of Muirgen will be to strike as robust a "right to repair" systems as possible while ensuring the collected maps are affordable for as many users as possible. I wish we lived in a world where navigation maps data was a public service, but that's not the case.

## 1. System Objectives
- Provide a mathematically secure framework to satisfy Hydrographic Office (HO) anti-piracy OEM requirements.
- Ensure 100% offline capability.
- Guarantee a "Right-to-Repair" failover mechanism that prevents data loss mid-voyage due to hardware failures.
- Minimize bandwidth overhead over satellite/restricted connections.

## 2. The Two-Tier Cryptography Model (Muirgen PKI)
Muirgen utilizes a hybrid cryptographic envelope to separate the heavy chart data from the decryption keys.

### 2.1 Bulk Data Encryption (Symmetric)
All S-57 vector charts are compiled into an MBTiles database and encrypted on the server using AES-256 with a randomly generated `ChartKey`. This bulk file is identical for all users and requires no bandwidth to recover if hardware fails.

### 2.2 License File Binding (Asymmetric)
The server encrypts the `ChartKey` using the user's specific Ed25519 Public Key. This generates a microscopic (1KB) License File.

## 3. Hardware Fingerprinting & Vessel Clusters
To prevent casual private key cloning (The Analog Hole), Muirgen binds the Private Key to the hardware.

### 3.1 Hardware Identifiers
The fingerprint is generated by hashing stable hardware identifiers:
- SoC Serial Number (e.g., `cat /proc/cpuinfo`)
- Onboard NIC MAC Address

### 3.2 The Floating Network License (Vessel Cluster)
To support mid-voyage hardware failover without requiring an internet connection:
1. Users register a "Vessel Cluster" containing up to 3 authorized hardware nodes (e.g., Primary MFD, Secondary MFD, NMEA Node).
2. The License File contains the `ChartKey` encrypted for *all* authorized Public Keys in the cluster.
3. If the Primary MFD fails and is replaced with a blank node, the blank node broadcasts a decryption request over the local LAN.
4. A surviving authorized node intercepts the request, decrypts the `ChartKey` locally, and securely passes the plaintext key to the new node to unlock the charts.

## 4. Hardware Failover Recovery Protocol (Offline/Iridium)
If the entire cluster fails and a spare must be initialized without local peers:
1. The new hardware generates a new Ed25519 keypair and hardware fingerprint.
2. The user emails the new Public Key to the Muirgen automated server via Iridium GO!/satellite.
3. The server revokes the old keys, re-encrypts the `ChartKey` for the new Public Key, and emails back a new 1KB License File.
4. The user imports the License File, instantly unlocking the massive local map database without re-downloading it.
